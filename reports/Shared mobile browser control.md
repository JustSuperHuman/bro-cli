# Keep Chrome State Through Mobile Takeover

Keep the user's existing Chrome tab running on Windows and let the phone or Bro GUI control that tab through an authenticated pixel stream. This is the practical way to preserve the user's current sign-ins, unsent forms, and live JavaScript state through an agent-to-human handoff. Bro should provide the shared viewer and authentication boundary; JustBrowse should retain tab ownership and enforce the switch between agent and human input. A dedicated Chrome window can hold the same tab, while an actual Linux Docker browser needs its own profile and authentication lifecycle. Windows profile encryption and device-bound credentials prevent a general promise that copying a profile or cookies into Docker will preserve the session. This report proposes the implementation and acceptance criteria from the research notes; the complete feature has not been implemented or tested by this research task. ([Research notes](../research_notes/Shared%20mobile%20browser%20control/session-continuity.md), [Chrome cookie encryption](https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html?m=1), [Device-bound sessions](https://developer.chrome.com/blog/dbsc-windows-announcement?hl=en))

## The original tab preserves the state Docker cannot import

**The same live tab is the continuity boundary.** Moving that tab into a normal dedicated Chrome window retains its browser process and profile environment. The extension already has a move-tab tool using `chrome.windows.create({tabId, focused})` or `chrome.tabs.move`. Record the source window, tab index, active state, and focus before the move. Retain the tab ID throughout the handoff and return it to its original window when that window still exists. A dedicated window limits the surface shown to the human; it provides no operating-system isolation. ([Existing move tool](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/tools/browser/move-tab.ts), [Chrome window creation](https://developer.chrome.com/docs/extensions/reference/api/windows#method-create), [Chrome tab movement](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-move))

The requirement to preserve "exact state" needs a precise contract: the handoff itself must not reload, duplicate, or replace the tab, and it must not export and reconstruct its storage. The user and the website can still change state during the interaction. Background JavaScript continues to run, authentication can expire, and a user can intentionally navigate. Cookies and origin storage follow Chrome's normal sharing rules across tabs; `sessionStorage` remains specific to its tab. A renderer discarded by Chrome reloads on activation, so discard and freeze state must be visible in the handoff status. Preserving the same tab offers the strongest available continuity, with an explicit failure when that continuity is lost. ([Session-storage scope](https://playwright.dev/docs/auth#session-storage), [Chrome tab lifecycle](https://developer.chrome.com/docs/extensions/reference/api/tabs))

Copying the Windows profile into a Linux browser is a different product. Chromium documents that two running browser instances cannot share a user-data directory. Chrome's App-Bound Encryption ties protected data to the machine, while its Windows encryption code validates the user and application environment. Device Bound Session Credentials introduce a further dependency on a device-held private key; Google announced default availability for Workspace users in May 2026. These constraints rule out a general guarantee that profile mounts or copied cookies reproduce the user's sign-ins in a container. Playwright storage state can help bootstrap selected applications, but it does not checkpoint the renderer, and its documented treatment of `sessionStorage` requires separate handling. ([Chromium user-data directory](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/user_data_dir.md), [Windows encryption implementation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/os_crypt/README.md), [Workspace DBSC rollout](https://workspaceupdates.googleblog.com/2026/05/prevent-account-takeovers-with-DBSC-now-generally-available-in-the-Chrome-browser-for-Windows.html), [Playwright authentication](https://playwright.dev/docs/auth#session-storage))

| Provider | State contract | Isolation | Recommended use |
|---|---|---|---|
| Existing host tab | Retains the live tab and its existing authentication environment, subject to Chrome and website lifecycle changes | Existing Chrome profile permissions | Default for agent help and continuity |
| Existing tab in a dedicated normal window | Same contract as the existing host tab; save placement for return | Separate visual surface within the same host browser | Optional presentation for human takeover |
| Linux Chromium in Docker with a persistent profile volume | Own live state and logins after enrollment; no promise of parity with Windows Chrome | Container boundary, subject to its deployment configuration | Explicit isolated-browser provider |
| Selected storage export and import | Application-specific authentication bootstrap; no arbitrary renderer memory or device-bound keys | Depends on the destination provider | Separate experimental capability with per-site validation |

A container can host the relay or viewer while the controlled Chrome tab remains on Windows. Label that arrangement as a connection to the host browser. If a real container browser is required, expose it through the same viewer protocol with a distinct provider ID and a visible independent-login requirement. Do not silently switch providers during a waiting handoff. Chrome 136 also changed remote-debugging flags so the default data directory is unavailable through that launch route; the existing extension debugger transport avoids designing this feature around a new default-profile debugging launch. ([Chrome remote-debugging change](https://developer.chrome.com/blog/remote-debugging-port?hl=en))

|---|---|---|

| `F:/bro-cli-v2` | Browser registry and paired routes, hosted viewer assets, frame/input socket, session notifications, and GUI entry | Bridge router and shared `AppState`; palette command and Wry WebView machinery |

JustBrowse already prepares explicit tab claims before executing tools and persists session leases in `chrome.storage.session`. Its CDP manager shares attachments by owner and serializes commands per tab. Extend those components so the originating MCP session keeps its tab claim throughout human interaction, while a separate controller lease determines who can mutate the page. The current context-free tool path bypasses the browser session manager; close that bypass for every tab effect, including commands that execute JavaScript. A guard only in Bro would leave another native tool caller able to race the human. ([Tool dispatcher](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/tools/index.ts), [Session manager](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/tools/browser-session-manager.ts), [CDP manager](F:/chromemcp/JustBrowseMCP/app/chrome-extension/utils/cdp-session-manager.ts))

Add a browser routes module beside `rmm::routes` in the Bro router. Give it its own path validation and the same requirement for paired authorization, including local requests. The existing RMM middleware deliberately suppresses the ordinary loopback exemption, checks cross-site browser requests, and applies no-store, no-referrer, and nosniff headers. Reuse those protections through a shared helper or equivalent browser middleware. Keep the JustBrowse native listener on loopback. Its present Origin allowlist and allowance for requests without Origin are not a replacement for authenticated browser-control capabilities. ([Bridge router](F:/bro-cli-v2/crates/bro-bridge/src/server.rs), [RMM authorization](F:/bro-cli-v2/crates/bro-bridge/src/rmm.rs), [Native Origin validation](F:/chromemcp/JustBrowseMCP/app/native-server/src/server/cors-origin.ts))

The proposed Bro surface is a status/list route, a handoff create/claim route, controller heartbeat and release routes, a completion route, and a socket for frame and control traffic. Route names remain an implementation choice. Bind every handoff to a Bro session, originating MCP session, provider incarnation, and exact target tab. Expose an opaque target handle to clients. A control message should carry the following logical fields; the gateway resolves their authoritative values instead of trusting client-selected tab IDs.

```text
handoffId, targetHandle, providerIncarnation, controlEpoch,
inputSeq, geometryId, lastFrameSeq, type, payload
```

Allocate `inputSeq` in delivery order after local motion coalescing. A new controller receives a new epoch and sequence space. Reject wrong epochs, wrong targets, and geometry mismatches; acknowledge a duplicate sequence without applying it twice. An ordered input stream must not replay old events after reconnection. Frame sequence identifies what the human saw, while geometry ID identifies the transform needed for input. A fresh frame can share geometry with an older frame, so requiring every click to reference the newest transmitted image would create avoidable failures on a slow connection. These are proposed protocol rules, not capabilities found in the current bridge.

Native messaging currently handles request/response commands and wraps extension tool results inside an outer success response. New streaming events need a separate message type and correlation path so frames cannot complete unrelated tool requests. Inspect both outer transport status and inner `ToolResult.isError`. Native messaging allows larger messages from extension to host than in the reverse direction, but its message-size ceilings should not become queue budgets. Keep frames bounded and convert to an efficient socket representation at the Bro gateway. ([Native host](F:/chromemcp/JustBrowseMCP/app/native-server/src/native-messaging-host.ts), [Extension native dispatch](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/native-host.ts), [Chrome native messaging limits](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging))

Host the viewer once in Bro. The phone can display it in its existing WebView dependency, and the GUI can use Wry. The mobile wrapper owns safe areas, hardware-back close, background cleanup, and network errors; the hosted page owns browser navigation and input geometry. Place a persistent Browser entry beside remote desktop and a session-specific entry on an agent's waiting interaction. A desktop palette command can open the same bridge-owned page, following `Services::open_voice_page`. Existing Wry Apps machinery has useful embedding code, although its conversation-card assumptions need adaptation. The mobile repository requires exact Expo SDK 56 documentation before implementation. ([Mobile instructions](F:/bro-cli-mobile/AGENTS.md), [Expo SDK 56 WebView](https://docs.expo.dev/versions/v56.0.0/sdk/webview/), [Mobile terminal integration](F:/bro-cli-mobile/src/TerminalScreen.tsx), [Chat controls](F:/bro-cli-mobile/src/components/ChatsScreen.tsx), [Mobile modal](F:/bro-cli-mobile/src/components/remote/RemoteDesktopScreen.tsx), [Desktop page-opening pattern](F:/bro-cli-v2/crates/bro-tui/src/services/live_voice.rs), [Wry embedding](F:/bro-cli-v2/crates/bro-tui/src/app/gui/apps.rs))

## An enforced handoff separates ownership from connection health

**Losing the phone connection must not resume the agent.** The originating MCP tab claim, the handoff hold, and the current human controller lease serve different purposes. The claim keeps other agent sessions away from the tab. The hold blocks agent mutations until the handoff finishes. The renewable controller lease permits one authenticated client to send input while other authorized clients can watch. Lease expiry releases the writer; the hold remains. This resolves the research notes' two disconnect concerns: release unattended input ownership, and preserve the waiting task for reconnection.

The extension must apply state transitions and tool admission under the same per-tab serialization boundary used for effects. Installing the hold prevents new agent mutations, then a barrier waits for already admitted work to complete. A click already sent to Chrome cannot be undone. If an admitted action times out with an uncertain result, report recovery required before offering human input. Treat unknown methods and arbitrary `Runtime.evaluate` calls as effectful unless the system has a proven safe classification. A prompt asking the agent to pause is useful context, but it cannot enforce this boundary. ([Existing dispatcher](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/tools/index.ts), [Per-tab CDP serialization](F:/chromemcp/JustBrowseMCP/app/chrome-extension/utils/cdp-session-manager.ts))

The following state machine is the proposed authoritative contract. A viewer connection is independent of these states. `Done` means completion; closing a modal or losing a socket only suspends control.

| State | Admitted mutations | Event and required transition |
|---|---|---|
| `AGENT_ACTIVE` | Originating agent through its existing tab claim | A validated human-help request atomically installs the hold and enters `PAUSE_PENDING`. A manually opened browser view must use the same takeover operation before gaining input. |
| `PAUSE_PENDING` | Only work already admitted before the hold; no human input | Drain the per-tab barrier and enter `HUMAN_WAITING`. An uncertain in-flight result enters `RECOVERY_REQUIRED`. A cancellation enters `RETURNING` so cleanup and release still occur. |
| `HUMAN_WAITING` | No agent or human mutations | Claim from an authorized viewer creates a new control epoch and enters `HUMAN_CONTROLLED`. Explicit cancellation or completion enters `RETURNING`. |
| `HUMAN_CONTROLLED` | One controller with current epoch, target, and ordered input | Heartbeats renew that controller. Disconnect, expiry, app background, or viewer close revokes its input and enters `HUMAN_SUSPENDED`. `Done` or explicit return enters `RETURNING`. |
| `HUMAN_SUSPENDED` | No agent or human mutations | Reclaim by an authorized client issues a new epoch and returns to `HUMAN_CONTROLLED`. Explicit completion or abandonment enters `RETURNING`. Elapsed time alone never releases the agent hold. |
| `RETURNING` | No new input from either side | Invalidate the human epoch, drain accepted input, cancel pressed buttons/touches, remove temporary emulation, and restore placement when possible. Release the hold only after required cleanup and target validation succeed, then enter `AGENT_ACTIVE` and publish one completion event. Uncertain cleanup enters `RECOVERY_REQUIRED`. |
| `RECOVERY_REQUIRED` | No mutations until reconciliation | Preserve the hold. Reattach only to the recorded tab in the recorded provider incarnation. Verified recovery returns to `HUMAN_WAITING`, with a fresh epoch on the next claim. Explicit abandonment uses `RETURNING` if the target is still valid. A missing target enters `CLOSED`. |
| `CLOSED` | None | Revoke all capabilities, stop capture, and report that continuity ended. Do not select a replacement tab. A new browser interaction requires a new handoff. |

Debugger detach, tab discard, and a provider restart must interrupt control and trigger reconciliation. Chrome's debugger API reports detach when the tab closes or DevTools takes over; enterprise restrictions can also prevent attachment. Persist handoff metadata separately from frames, using the extension's session storage for suspension recovery and Bro's registry for client status. After a Bro restart, reconcile with the extension before granting input. After a browser restart or loss of the authoritative ownership record, require explicit recovery; a reused numeric tab ID must never inherit an old capability. ([Debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger), [Existing persisted claims](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/tools/browser-session-manager.ts), [Bro shared state](F:/bro-cli-v2/crates/bro-bridge/src/state.rs))

Restore the recorded tab index and active state when its source window survives. If that window closed, keep the same tab in a valid normal window and report the placement change; preserving the tab has priority over recreating a vanished window arrangement. A cleanup failure that leaves unknown emulation or pending input requires recovery before agent admission. Registered popups need explicit target ownership and a deliberate target switch; an untracked new tab must not receive inherited control. On successful return, notify the originating Bro session with the handoff ID, target, and outcome. The resumed agent must obtain a fresh page snapshot because the human has changed the page. The research did not establish an existing agent pause/resume transport, so wiring that notification into each supported agent runtime remains implementation work. ([Bro session state](F:/bro-cli-v2/crates/bro-bridge/src/state.rs))

## Bounded frames and CSS input make the phone usable

Use `Page.startScreencast` through the existing extension debugger attachment, with one long-lived capture owner per tab. The command supports JPEG or PNG, quality, dimensions, and frame sampling; its events require `Page.screencastFrameAck`. Current protocol source contains optional flow-control improvements, but installed Chrome support must be negotiated. Do not make tip-of-tree parameters a minimum assumption. The existing screenshot tool's one-frame screencast fallback calls `stopScreencast`, so it needs arbitration with the live stream: serve its capture from the shared owner or use a compatible capture path that cannot stop another consumer's stream. ([CDP Page protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Page.pdl), [Screenshot fallback](F:/chromemcp/JustBrowseMCP/app/chrome-extension/entrypoints/background/tools/browser/screenshot.ts))

Keep one newest decoded-or-ready frame per viewer and one latest cached frame for joining viewers. Bound native and socket queues as well. A slow observer must not block the controller or other viewers. Acknowledge each CDP frame after accepting it into bounded storage or deliberately dropping it; a separate viewer acknowledgment controls whether that viewer can receive another frame. Waiting for every phone to display a frame before acknowledging Chrome couples capture to the slowest network. Sending every frame into an unbounded WebSocket queue converts bandwidth pressure into stale interaction. Stop capture when no viewers remain, with an optional bounded reconnect grace, while keeping the tab and handoff hold alive. JPEG quality 65 is a proposed starting value from the notes, not a measured optimum. Measure image quality, bytes, and latency before choosing final budgets. ([Protocol flow control](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Page.pdl), [Streaming proposal and transport constraints](../research_notes/Shared%20mobile%20browser%20control/bridge-implementation.md))

The input coordinate space is the remote main-frame viewport in CSS pixels. Image pixels, device pixels, and document scroll coordinates are different spaces. First invert the viewer's contain sizing, letterboxing, zoom, and pan. Then apply the frame's validated remote geometry transform. Publish CSS viewport dimensions separately from encoded image dimensions, include a geometry version, and reject events outside the displayed page rectangle. Do not multiply by the phone's `devicePixelRatio` or add document scroll offsets to viewport input. DevTools' screencast implementation accounts for scale and `offsetTop`; use it as an implementation reference, then prove the transform against the installed Chrome build at browser zoom and page-scale combinations. The notes explicitly leave that mapping test unresolved. ([CDP Input protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl), [DevTools screencast geometry](https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/panels/screencast/ScreencastView.ts), [DevTools input mapping](https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/panels/screencast/InputModel.ts), [Geometry research gap](../research_notes/Shared%20mobile%20browser%20control/mobile-integration.md))

Retain the current page viewport by default. Offer mobile layout as an explicit action because `Emulation.setDeviceMetricsOverride` changes viewport and mobile-layout behavior. Save and restore any prior override and relevant window geometry; do not reload or silently change the user agent to obtain a mobile layout. Responsive resizing can change application state even while the tab survives. The viewer itself should adapt to the phone's safe area and visible viewport, including keyboard-induced size changes. ([CDP Emulation](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Emulation.pdl), [VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport), [Viewer element geometry](https://developer.mozilla.org/en-US/docs/Web/API/Element/getBoundingClientRect))

A practical first input model is tap for click, one-finger movement for wheel scrolling, and an explicit drag mode for sliders or selection. Coalesce expendable pointer movement and accumulated wheel deltas before dispatch; retain ordered press/release, key, and text events. Treat local two-finger pinch as viewer zoom and account for the resulting transform. If a site needs actual touch events, provide an explicit touch mode and use proper end/cancel events, with empty touch-point lists as required. Do not emit mouse and touch sequences for one gesture. Release active buttons and cancel touches when ownership changes. Pointer Events and `touch-action` help prevent the local WebView from consuming a gesture intended for the remote page. ([CDP Input](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl), [Pointer Events](https://w3c.github.io/pointerevents/))

Open the phone keyboard through a local input element and send committed text through `Input.insertText`. Send Enter, Backspace, Tab, and navigation keys through key events. Respect composition boundaries so IME text appears once, and use text insertion for deliberate paste. The viewer should show its connection and controller state and provide an accessible keyboard route for its controls. Follow the app's existing graphite palette and Inter typography. Keyboard and pointer behavior need physical-device validation; the presence of a WebView dependency does not establish that behavior. ([Input text support](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl), [Mobile theme](F:/bro-cli-mobile/src/theme.ts))

**The stream grants access to signed-in page content.** Scope view and control permissions separately to the authorized handoff. Keep the long-lived pairing token out of viewer URLs and logs. A proposed socket bootstrap is an authenticated API request for a short-lived, single-use connection ticket, followed by first-message socket authentication; unauthenticated sockets cannot subscribe or send input. Validate browser Origin for hosted clients, enforce exact target binding, and redact tokens, frame payloads, and typed text from ordinary diagnostics. Keep controls behind a narrow allowlist for pointer, text, selected keys, and navigation. Reject arbitrary CDP, arbitrary JavaScript, and privileged navigation schemes such as `javascript:`, `file:`, or `chrome:`. Do not synchronize the system clipboard automatically. These restrictions are proposed additions to Bro's existing paired-request checks. ([Current paired-request boundary](F:/bro-cli-v2/crates/bro-bridge/src/rmm.rs), [Current native Origin policy](F:/chromemcp/JustBrowseMCP/app/native-server/src/server/cors-origin.ts))

Page pixels do not guarantee access to native permission sheets, passkey dialogs, password-manager UI, file pickers, or protected media. Give the human a route into the existing remote desktop surface while retaining the same agent hold. Verify the human's authority when switching surfaces. The product should report when the page stream cannot complete an interaction; it must not claim that a blank or unchanged page proves the action succeeded. Rendering while minimized, occluded, inactive, or behind a locked display also remains a live-test requirement. ([Debugger surface](https://developer.chrome.com/docs/extensions/reference/api/debugger), [Recorded limitations](../research_notes/Shared%20mobile%20browser%20control/session-continuity.md), [Existing desktop screen](F:/bro-cli-mobile/src/components/remote/RemoteDesktopScreen.tsx))

## Acceptance requires a live tab round trip

The bridge researcher recorded four extension test files with 19 passing tests and three native-server suites with 52 passing tests. The selected native suites needed coverage disabled after the initial command failed unrelated whole-project coverage thresholds. Those checks cover existing ownership, transport, and movement behavior; they do not exercise a mobile handoff. This report has not rerun them. No end-to-end latency, device-input, Docker-transfer, or installed-Bro result appears in the research notes. ([Recorded baseline commands and outcomes](../research_notes/Shared%20mobile%20browser%20control/bridge-implementation.md))

Build a controlled origin before involving third-party accounts. Seed a server cookie, local storage, IndexedDB, tab-specific session storage, unsent form text, scroll position, and a random JavaScript value never written to storage. Record tab identity and navigation/reload events. The agent requests help, the human edits through the viewer, and the agent resumes against that exact tab. Test a popup separately with explicit ownership. This fixture distinguishes preserved live state from a convincing-looking reload restored from cookies. The matrix below defines proposed acceptance; every row remains pending implementation validation.

| Area | Exercise | Required evidence and passing behavior | Current evidence |
|---|---|---|---|
| Live state | Agent → waiting → mobile input → Done → agent | Stable original tab; no handoff-induced reload; in-memory value and unsent edits preserved; human edits visible to the resumed agent | Proposed fixture only |
| Authentication | Use an existing signed-in host tab, including a device-bound flow where available | Site accepts the same browser environment through takeover; no credential export or unexpected provider switch | Primary-source constraints; no live account test |
| Profile sharing | Change same-origin cookie and origin storage, compare another host tab | Browser-normal sharing; the other tab retains its own session storage | Proposed test only |
| Agent barrier | Request takeover during an admitted agent action; try contextual and context-free mutations afterward | Earlier action drains or reports uncertainty; every later mutation is rejected until return; unrelated leased tabs remain untouched | Existing claim/serialization tests; new barrier untested |
| Competing humans | Connect phone and GUI, claim from both, replay an old epoch and duplicate sequence | One writer; observers remain read-only; old input cannot mutate; duplicate action is not repeated | Proposed protocol only |
| Disconnect | Drop network or background the app during an edit, then reconnect | Controller revoked; original tab and edit survive; agent remains held; new epoch required | Proposed lifecycle only |
| Completion | Select Done while input is in flight | Drain/cancel completes before one resume event; new human input rejected; agent receives fresh-page requirement | Proposed lifecycle only |
| Geometry | Tap edges and letterboxes; rotate; change viewer zoom, browser zoom, page scale, and keyboard visibility | DOM-recorded targets match displayed targets; outside-page events rejected; stale geometry rejected | Protocol references; transform unverified |
| Text and gestures | Unicode, emoji, IME composition, paste, Enter, Backspace, scrolling, selection, slider drag | Text commits once; controls behave correctly; no stuck buttons/touches or duplicate synthetic gestures | Existing input primitives; device behavior untested |
| Backpressure | Slow or stop a viewer while another watches; run screenshot capture concurrently | Bounded queues and memory; old frames dropped; slow viewer cannot stall others; screenshot cannot stop live stream | Existing screenshot tests; remote capture untested |
| Target loss | Open DevTools, close/discard the tab, restart bridge or browser, close the source window | Explicit recovery/closed state; no replacement target; original-tab placement fallback documented; stale capabilities invalidated | Existing detach primitives; recovery untested |
| Native UI | Trigger permission, file, or passkey interaction | Clear desktop fallback; agent stays held; no false success from page pixels | Limitation identified; fallback untested |
| Authentication boundary | Missing/expired ticket, wrong Origin, wrong session/target, privileged URL, raw CDP attempt | Rejected before subscription or effect; sensitive content absent from routine logs | Existing paired middleware and native Origin tests; new routes untested |

Measure displayed-frame age, input-to-visible-update delay, transferred bytes, and memory under a slow connection. Set release thresholds from those measurements and the intended phone network; the notes supply no defensible numerical latency target. Start with the controlled continuity fixture and ownership barrier, then validate shared viewing and physical-device input. A Docker provider gets its own enrollment and acceptance run because a successful host-tab handoff supplies no evidence of cross-platform profile migration.

## Conclusion

The hard engineering boundary is the point at which one controller loses authority and another gains it. Put that boundary next to JustBrowse's actual tab effects, then let Bro distribute the resulting state and pixels to its clients. This permits the mobile screen and desktop GUI to evolve without weakening ownership enforcement.

If strict container isolation becomes a requirement, make provider selection an explicit choice before the agent starts the task. A task that depends on Windows-held authentication should remain attached to that host browser; a task started in an enrolled container browser can keep its own live state through the same handoff protocol. Provider identity then becomes part of the task's state contract, and acceptance can verify that contract directly.
